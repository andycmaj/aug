Riker

Your first officer, in a terminal. It triages GitHub and Slack and drafts your replies, but that is only part of the job: it also runs your crew of Claude agents, starting and stopping them, tracking tasks, projects and worktrees, and keeping the work moving.

Packages and plugins

A bun workspace under packages/*. A package imports another by name (@riker/core/store) from its src/; nothing is built, and one tsconfig.json and one bun test cover them all. Dependencies run one way, and packages/core/test/boundaries.test.ts fails on an import that goes the other way.

cli→tui→fixtures→triage · github · slack→core→code-review-plannotator

What a plugin brings: RikerPlugin (core/plugins.ts)

An entry point hands the engine its list: rikerPlugins() in tui/src/plugins.ts ([triagePlugin(), githubPlugin(), slackPlugin()]), which index.tsx and riker-tools both read; the fixture day and the sim pass their own. Core runs what they bring without importing them. A test picks only what it drives: githubPlugin({ api, prs, clock }), slackPlugin({ transport, remoteLink }).

Triage: a chain of rules, then the Inbox

Pollers only insert into messages (the inbox) and save their cursor. The engine's one worker claims due rows oldest first and hands them to the triage plugin's Triage.next; a burst on one thread (within BATCH_WINDOW_MS, 2 min) is one run on the latest, carrying all their text. Each rule returns ok(outcome) to claim a message or pass(why) to hand it on, in the order of TRIAGE_RULES. The model's verdict is asked at most once, so a message a gate claims costs nothing. Every run is recorded (triage_runs, one triage_steps row per rule tried) and shown on the Board's Inbox tab. Pick a message to see where it stops. packages/triage/src/triage.ts

    Agent lifecycle

    A task's agent_state summarizes its newest session. Every change is one named transition in core/lifecycle.ts; nothing else writes those columns. However a session ended (your Stop, a closed window, claude exiting, a restart), the task is stopped and Start resumes it; the reason is on the session. The marks are the ones the rail and Board draw (core/lanes.ts). Click a state or a transition.

      Moves bus

      Other processes (the Assistant, a task's agent, a hook) never touch the desk directly. They ask for a move through a SQLite table, and the engine runs it. One registry in core/moves.ts (verb, args, help, run) feeds riker-tools move <verb>, the Assistant's prompt and the engine's dispatch. A new verb goes in the registry, nowhere else.

      1. riker-tools move <verb> inserts a moves row (pending, asked_by) and waits.
      2. The commit bumps PRAGMA data_version; the engine notices and drains. A move older than a minute expires: no Riker was running to make it.
      3. runMove checks the verb and required args; for an agent, AGENT_MOVES on its own task or one it made (from_task_id; the onboarding interview may only propose_doc).
      4. Each plugin's move guards run next: from Slack, CONFIRM_MOVES wait for your yes in that thread (@riker/slack confirm.ts).
      5. The spec's run acts on the desk, recorded for ctrl+z (core/undo.ts). A move that would open a dialog answers needs … in words.
      6. One result line goes back on the row; riker-tools prints it.
      # the Assistant, from Home
$ riker-tools move priority RIKER-0012 --level urgent
RIKER-0012 is urgent

# a task's own agent asking for an owner's move
$ riker-tools move start RIKER-0031
start is the owner's move: say what you need under Next steps

# a task action, by name (no name lists the ones that apply)
$ riker-tools move action RIKER-0031 summarize

      Actions and commands

      Three registries, one place they land. Keys are the owner's, in the TUI (tui/src/keymap.ts), and the : palette lists the same set. Moves are what other processes ask for (above). Task actions are skills Riker runs on one task (core/task-actions.ts). Every one of them ends on a desk method, so a thing done by key, by palette, by the Assistant or by a trigger behaves the same. Pick a door to see the path.

        Task actions: skills on a task

        The recipe is a skill (SKILL.md: prompt, allowed-tools); Riker adds only which rows it applies to, how it runs and where the answer goes. Built-ins ship in Riker's own Claude Code plugin (packages/core/plugin, written under RIKER_HOME/plugin and loaded with --plugin-dir, so nothing needs installing). Config actions changes one field by field, turns one off (false) or registers another; a bare user skill is wrapped in a plugin of its own and refused if its allowed-tools widen the grant. An action never touches agent_state: its answer is a TurnRole.action turn, never the agent's.

        actionskillviaoutputapplies to
        triggerson runs an action with no key: plain rules, no model (kind, channel, githubReason, and case-blind regexes on author, title, body, plus project). triaged fires from desk.afterTriage; ready, merged and done come from task_events read every 2 s past a kv cursor, so a done from riker-tools in another process is heard. action_runs keeps each one to once per task, action and event. Auto runs go one at a time, never past the day's spend cap, and never a pane action.

        The palette

        tui/src/palette.ts lists the bindings the footer and ? help show (helpBindings), one entry per command with movement left out, plus the moves that have no key and one Action: … entry per task action that applies to the row. It opens on Context (the pane's and the row's entries, flat, titled for the row through each view's subject); tab shows All (app-wide and keyless too, grouped). A key's entry runs through keymap.dispatchCommand on the pane under it, so it does exactly what the key does. The mode is paletteMode on the Riker context.

        Guided review

        The guide action writes a guided code review of a coding task's change: chapters that walk the diff in a sensible order, with review findings pinned to their lines, saved into Plannotator and opened there on the Canvas. The work is @riker/code-review-plannotator, a library that knows nothing of Riker; Riker's glue is core/run-action.ts and core/guide-turn.ts. A pull request review that triage files is a coding task whose brief is this review, and it offers the guide on arrival: running it makes the PR's worktree with no agent, and its review opens on the PR in Plannotator, whose Post to GitHub sends yours. Step through a run on the map with the Guide action flow; the stages are below.

          How a big change is batched

          Every file's diff goes into exactly one prompt, so nothing depends on the model choosing to read it, and related files share a batch so a finding that needs both is in reach. No parser: batches.ts relates files by plain signals.

              Without Riker

              review() runs it end to end with any ask. claudeAsk is one on a fresh, read-only claude -p (no user settings, hooks, MCP or saved session) that keeps each call's cost and tokens, so runs compare. RIKER-0188 builds the eval harness on this: the same changes at several batch sizes and models, findings compared, and a batchTokens setting per action for whatever budget wins.

              Inverting core's dependency on code review · RIKER-0190

              The split made the review a package, but core still depends on it: the only @riker/* import core is allowed (ALLOWED.core = ["code-review-plannotator"] in boundaries.test.ts). The plan is to make code review a plugin core is agnostic about, through the same RikerPlugin seam the connections use (RIKER-0198 asked for a field there, not a new registry).

              One door each

              Most of the architecture is a set of single owners. When you need to change one of these things, there is exactly one file to open.

              Store

              bun:sqlite at ~/.riker/riker.db (RIKER_HOME overrides). Row shapes in core/types.ts mirror the tables one to one. Hooks and riker-tools in other processes write here. Triggers bump a counter per table in table_versions, so a write from any process says what it touched, and each read in core/read-model.ts re-runs only when a table it names changes. Perf counters live in their own perf.db, so a flush never moves riker.db's data_version.
